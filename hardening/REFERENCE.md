# Hardening reference

Detail behind [README.md](README.md): every hook, the decision protocol, subagent scopes, the MCP policy, the security model and how to test and debug.

## Registration

All hooks are registered by [settings.hooks.json](settings.hooks.json) as one plain shell string per hook:

```json
{ "type": "command", "command": "node hardening/hooks/pre-tool-use.mjs", "timeout": 20 }
```

Claude Code runs shell-form commands in Git Bash (PowerShell when Git Bash is missing) from the session's current folder,
with `CLAUDE_PROJECT_DIR` exported: that folder is the project root until a `cd` moves the main session (below). GitHub Copilot CLI also reads
`.claude/settings.json` and `.claude/settings.local.json` (in a folder trusted in the CLI) and runs the string in
PowerShell on Windows and bash elsewhere, from the repository root, with `CLAUDE_PROJECT_DIR` exported too (Copilot CLI
1.0.94 and Claude Code 2.1.293, probed 2026-10-08). The string therefore carries no `args` (the CLI ignores them and
runs bare `node`, which fails on the payload and then refuses every tool), no `${CLAUDE_PROJECT_DIR}` (the CLI does not
substitute it and PowerShell expands it to nothing) and no quotes or inline code (the CLI's PowerShell call drops them).
Claude Code's docs recommend `${CLAUDE_PROJECT_DIR}` for a hook that must run from any working directory; the relative
form is used because the CLI accepts nothing else, and the guard keeps Claude Code's main session at the root so that it
works there too (below). The payload always arrives as JSON on stdin; environment variables such as `$TOOL_INPUT` are empty and must never
be used. A hook that cannot start does not block (Claude Code docs, Hooks), which is why the installer refuses the pack
without Node 18.17+ on PATH. Neither does one that times out, so git cannot hold a hook that long: one git call times out
after 3 s (`BI_HARNESS_GIT_TIMEOUT_MS` raises it to at most 10 s) and all git calls of one hook process share 12 s; the
Stop gate's share 60 s under Claude Code (90 s in this file) and 20 s under Copilot CLI and VS Code (`BI_HARNESS_HOST`;
30 s in `copilot-cli.hooks.json` and `vscode.hooks.json`) or under the Copilot CLI's run of the Claude registration
(`COPILOT_CLI=1`, `copilotCliSignal`), each at least a third below its host's timeout, the Stop gate's wait for another
copy included (`gitBudgetMs` and `spendGitBudget`
in `hooks/lib/common.mjs`; `tests/self-protection.test.mjs` checks all three files; [README](README.md#limits), Slow
machines).
`tests/copilot-claude-dialect.test.mjs` runs the registered string through bash, `pwsh` and
`powershell` from a project copy, with and without `CLAUDE_PROJECT_DIR`.

**A `cd` strands the hooks.** Claude Code keeps a `cd` of the main session for the next call, so after `cd reports` every
hook runs from `reports/`, fails with a non-blocking "Cannot find module" error, and the guards stop. The PreToolUse guard
(`strandedCd` in `hooks/lib/policy.mjs`) therefore denies a Bash or PowerShell command whose `cd` would leave the main
session in a project subfolder. It makes no claim on a GitHub Copilot host (stranding was not shown there), in a
subagent's call (Claude Code carries a `cd` to the next call only in the main session), for either tool while
`CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR` is set (without it a PowerShell `Set-Location sub` was kept for the next call,
with it set to 1 the next call was back at the start folder; Claude Code 2.1.322 on Windows 11, probed 2026-11-10), and
for a `cd` back to the root, outside the project, to a folder it cannot place or inside a command string handed to
another process. In Bash a `cd` inside a subshell `( )` or `$( )` passes; one in a brace group or an `if` body counts.
PowerShell has no subshell: a `cd` inside `( )`, `$( )`, `@( )`, `{ }`, `if`, `try` or `& { }` counts (pwsh 7.6.9 and
Windows PowerShell 5.1 each left the session in the subfolder; 5.1 cannot parse `&&`), and
`Push-Location "x"; try { ... } finally { Pop-Location }` passes. The denial names the way out for its tool: paths from
the repository root, or `(cd "x" && ...)` in Bash and `Push-Location "x"; try { ... } finally { Pop-Location }` in
PowerShell (`tests/stranded-cd.test.mjs`). What it cannot see: [README](README.md#limits).

**Worktrees under `.claude/worktrees/` (2026-11-17).** A session whose project folder (`CLAUDE_PROJECT_DIR`) is itself a
worktree checkout there is judged by project-relative paths: ordinary writes to its files get the verdict they get in any
project; its own guardrail, reference and secret paths, the parent repository's and a sibling worktree's guardrail files,
any write that leaves the project and a link into the parent's `.claude/` or `hardening/` stay denied
(`tests/over-denials-2026-11-17.test.mjs`). A worktree outside `.claude/` opened as its own project
(`git worktree add ../x`, then Claude Code in that folder) works the same way.

**Worktree sessions.** The other configuration: `CLAUDE_PROJECT_DIR` is the main checkout and the hook payload's `cwd`
lies in a linked worktree `<main>/.claude/worktrees/<name>` (the desktop app's worktree sessions, `EnterWorktree`, a
subagent with worktree isolation). `hooks/lib/session-root.mjs` reads the payload before the policy loads and verifies
the worktree from files only, on canonical paths, with no git process (a git that times out would fail open) and no
environment variable: `cwd` is in a folder `W` exactly one segment below `<main>/.claude/worktrees/`, `<main>/.git` is a
directory, `W/.git` is a file `gitdir: G`, `G` is a direct child of `<main>/.git/worktrees/`, and `G/gitdir` names
`W/.git`. Then `PROJECT_DIR` is `W` for `pre-tool-use.mjs`, `agent-scope.mjs`, `post-tool-validate.mjs`, `stop-gate.mjs`
and `session-start.mjs`: the worktree's own files get the plain project's verdicts for the shell and for Edit, Write and
Read; its own guardrail, reference and secret paths and its `.git` file keep theirs; the post-edit validator and the Stop
gate check the worktree's files; an editor subagent's write globs, the banner and the protected-branch checks read the
worktree. `HOME_DIR`, the main checkout, keeps `hardening/harness.config.json`, the manifest and `.claude/logs/` with the
session state: a row written in a worktree session carries `worktree: "<name>"` (not the rows of `audit-log.mjs`,
`post-tool-redact.mjs` and `user-prompt-guard.mjs`, which never change root), and state that holds project-relative paths
(`changedFiles`, the Stop gate's block counters) is keyed per checkout. The permission rules of both checkouts count.
Nothing outside `W` is more permissive than before: a shell write that leaves `W` is denied (the main checkout's and a
sibling worktree's files, a link out of `W`, `..` and absolute spellings, `<main>/.git/worktrees/`), an Edit, Write or
Read of a target outside `W` keeps the deny or ask the main checkout's root gives it and is never answered as routine (an
edit that was auto-approved from there is left to Claude Code's own permission flow), and no file outside `W` is in an
editor subagent's scope. A folder that fails a check (not registered, a forged `.git` file, a junction to another place,
a nested clone, a worktree two segments deep), a GitHub Copilot host and every process that reads no payload this way (the validator CLI, the git
hooks) keep the main checkout as root, with the verdicts they had: there a shell write in the folder is still denied as a
guardrail write and an Edit or Write asks. `strandedCd`'s home in a worktree session is the worktree; a session in the
main checkout keeps its verdicts for `cd .claude/worktrees/<name>`. Known gap, on the strict side: MCP model writes are
recorded from the main checkout's root, so an export into a worktree's model folder is not recognised and the Stop gate
blocks once, then warns. Tests: `tests/worktree-sessions.test.mjs`.

**Measured live (2026-11-17).** Claude desktop app 5.11492.5, Agent SDK 0.3.325, Windows 11, with a logging hook in a
throw-away project that had the pack installed; both sessions were started by an agent through the app, and a worktree
session the user opens by hand in the app was not measured. In an app worktree session and in a subagent with worktree
isolation alike, `CLAUDE_PROJECT_DIR` is the main checkout and the payload's `cwd` is the worktree root
(`<main>/.claude/worktrees/<name>`; `agent-<id>` and an `agent_id` for the subagent), on SessionStart, PreToolUse and
Stop in the app's session and on SubagentStart, PreToolUse and SubagentStop in the subagent. Hooks registered only in
the git-ignored `.claude/settings.local.json` run in both, and both worktrees hold a copy of that file. The hook process runs from the main checkout in the app's worktree session, so the relative hook command
runs the main checkout's script; in the subagent it runs from the worktree, so it runs the worktree's own copy, at the
version of the commit the worktree was cut from (in this repository an agent's worktree sat at `main`'s commit while the
session's branch was two commits ahead). A hook whose file is not in the worktree did not run there at all: with a pack
that is not committed, a subagent with worktree isolation has no guard. The pack's log rows landed under the main checkout's `.claude/logs/`
only. Before this change the guard denied `echo hi > notes.txt` and asked for a Write of `docs/a.md` in both sessions
(seen live). With it, the hook run as a process on those two worktrees with the measured payloads gives both calls the
verdict of a session in the main checkout; that was not repeated in a live session. Not measured: `EnterWorktree`, the
CLI's `--worktree`, macOS and Linux, and how Claude Code itself evaluates root-anchored permission rules in a worktree
session.

**Subagents with worktree isolation (2026-11-18).** The live measurement above left a gap: such a subagent runs the
worktree's own copy of the hooks, so with `hardening/` not in its worktree it had no guard. The main session's guard
sees the call that starts it (tool `Agent`, `tool_input.isolation: "worktree"`), so `settings.hooks.json` now registers
a PreToolUse group with matcher `Agent` for `pre-tool-use.mjs` (an installed project gets it with
`install-into.mjs --update --enable-hooks`; the Copilot hook files are unchanged and the rule never applies under GitHub
Copilot). `hooks/lib/isolated-subagent.mjs` judges an `Agent` call that asks for worktree isolation: the `isolation`
argument, or `isolation: worktree` in the frontmatter of the custom subagent named by `subagent_type`, read from the
top-level `.md` files of `.claude/agents/` in the main checkout, in a worktree session's project and in the user's home.
It checks that `hardening/hooks/pre-tool-use.mjs` and `hardening/hooks/agent-scope.mjs` are in the commit the worktree
is cut from, as Claude Code's documentation ("Run parallel sessions with worktrees") states it: `origin/HEAD`, the
default branch on the remote, when that ref is cached; the local `HEAD` when no remote is named `origin`; the local
`HEAD` with
`"worktree": { "baseRef": "head" }` in the settings (managed settings win over local, local over project, project over
user). A settings file that cannot be parsed, or a `baseRef` that is neither `"fresh"` nor `"head"`, makes both refs
count. A file missing is a deny that names the ref and the ways out (commit `hardening/` to the branch worktrees are cut
from, set `baseRef` to `"head"` and commit it to the current branch, or start the subagent without worktree isolation).
A floor ask, in auto and lab mode too, when git gives no answer (never a pass), when a remote named `origin` has no
cached `origin/HEAD` (Claude Code fetches the default branch before it cuts the worktree, so the guard cannot know the
commit and `HEAD` alone proves nothing; `git remote set-head origin -a` caches it), when the missing files exist, git
ignores them and `.worktreeinclude` names them (the documentation has such files copied into new worktrees; the guard
cannot verify the copy), and when a settings file registers a `WorktreeCreate` hook. No verdict for any other `Agent`
call, in a folder without `.git`, and when the files are there. The session banner carries one line when a guard file is
missing from that commit. Limits: `origin/HEAD` is read as cached, while Claude Code fetches before it creates the
worktree; a subagent of a plugin, or one defined in a subfolder of `.claude/agents/`, with `isolation: worktree` in its
frontmatter and no `isolation` argument is not seen; a worktree cut from a commit with an older pack runs that older
guard; the tool's earlier name `Task` is not registered. Considered and not adopted: Claude Code's hooks reference names
`"onFailure": "block"` for a hook handler, which blocks the call when the hook cannot start. It would stop every call of
a subagent whose worktree lacks the pack. The same registration is read by GitHub Copilot CLI, where the field was not
probed, so it is not in `settings.hooks.json`. Not run in a live session: the rule was tested with the hook run as a
process (`tests/isolated-subagent.test.mjs`); the payload of the `Agent` call was measured live on 2026-11-17.

**Git on another checkout (2026-11-18).** `git -C <dir>` runs git in that folder like a `cd` there,
`git worktree remove --force` deletes a worktree folder with its uncommitted and untracked files like `rm -rf`, and
`git worktree move` moves one like `mv`; measured on `94dce45`, each passed where its plain spelling was denied. Now each
gets the stricter of its own verdict and the verdict of that plain spelling, judged by the same analysis: `git -C` when
the folder is another checkout (outside the project, as written or resolved: another repository, the main checkout or a
sibling worktree seen from a worktree session; or a folder of the project that holds its own `.git` entry, such as a
worktree under `.claude/worktrees/` or a nested clone); `git worktree remove` with `-f` or `--force`;
`git worktree move`. The program counts in every spelling the git rules know (`git.exe`, a path to it, behind `env`,
`command`, an assignment, `xargs` or `bash -c`, PowerShell's `&`). Measured, hook run as a process, 180 git spellings, 90
from the project root and 90 from a worktree session: 51 went from no verdict to deny (19 and 32) and none became
weaker. From a worktree session: `git -C <main checkout or another
repository> checkout -- <file>`, `restore <file>`, `checkout main`, also in PowerShell; from the project root:
`git -C .claude/worktrees/<name> checkout main`; from both: `git worktree remove --force <path>` (also `-f`, and through
`git -C`) and `git worktree move` of a worktree whose `mv` is denied. Unchanged: `git -C` into a folder inside the
project that is not a checkout of its own (`git -C hardening restore --staged hooks/x.mjs` keeps no verdict, which a test
asserts); `git -C <dir> switch main` and `status`, which have no verdict in their plain spelling either;
`git worktree remove` without force (git itself refuses a worktree with changed or untracked files), `prune`, `add`,
`lock`, `unlock`, `repair`, `list`; `git -C <worktree> add`, `commit`, `log`, `diff` from the main checkout stay routine.
A command whose plain spelling the guard cannot write back from its words is a floor ask. Tests:
`tests/git-other-checkout.test.mjs`.

**The installer sets the variable.** [settings.hooks.json](settings.hooks.json) carries
`"env": { "CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR": "1" }`, so the installer writes it into `env` of the settings file
that receives the hooks (`.claude/settings.local.json`, `.claude/settings.json` with `--shared`); the GitHub Copilot
registrations do not carry it. Set, it makes Claude Code return the Bash and PowerShell tools to the start folder after
each command of the main session, so a `cd` no longer strands the hooks. The merge keeps every other `env` entry and a
value of the variable already in the file, and the installer's output names that file and value. The manifest records a
variable the installer set (`mergedEnv`); `--update` removes one the harness no longer ships only while it still holds
the recorded value (`tests/install.test.mjs`). The guard stays the fallback: it judges a `cd` whenever the hook process
does not see the variable set to 1, true, yes or on. To keep that judgement instead, put a value of your own such as
`"0"` in the same file: the installer keeps it; deleting the entry does not last, because the next registration or
`--update` sets it again. Measured 2026-11-10 (Claude Code 2.1.322, Windows 11, headless `claude -p`, installed with
`--hardening --enable-hooks` into an empty Git repository, one run each; the probe above exported the variable in the
launching shell instead): with `"1"` in `env` of `.claude/settings.local.json` the guard denied neither a PowerShell
`Set-Location hardening` nor a Bash `cd hardening`, and the next call's `(Get-Location).Path` or `pwd` printed the
repository root; with `"1"` in `.claude/settings.json` (`--shared`) PowerShell did the same; with `"0"` in the local
file the guard denied `Set-Location hardening` as a stranded `cd`, so the hook process sees the value from the settings
`env`. Not measured: an interactive session, a folder the user has not trusted yet (Claude Code documents that most
`env` values of a project settings file apply only after trust), other Claude Code versions, macOS and Linux, and
whether Claude Code itself treats `"0"` as off. The risk that remains for a version not measured: a session that passed
the variable to its hooks without honouring it for its shell tools would get neither the return nor the denial; the
measured runs did not show it.

Statements, pipes and words are split quote-aware (`hooks/lib/shell-split.mjs`): a `;` or `|` inside quotes never ends a statement, so an editor keeps its file argument. A `#` that starts a word begins a comment (a quote inside it opens nothing, so the next line is a statement of its own), a carriage return alone ends a statement (PowerShell), bash's ANSI-C quoting is decoded (`$'\x2eenv'` is `.env`), and each command is also judged as bash and PowerShell read it without comments (`# …` to the line end, `<# … #>`); the strictest verdict wins. Each command is judged in every spelling its shell would run and the strictest verdict wins (routine needs every spelling routine): PowerShell drops a backtick before an ordinary character and joins a line that ends in one; bash drops a backslash before an ordinary character (`c\url`, `.\env`, `commit -\n`), joins `\<newline>` and reads `\\` as one backslash, while a Windows path (`docs\a.md`) is judged as written too. ## Subagent scopes

`agent-scope.mjs` reads `agent_type` from the payload and looks it up in `agentScopes` in `harness.config.json` (defaults in `hooks/lib/common.mjs`). The main agent has no scope. The hook's command takes no arguments: the flags `--read-only`, `--mcp-read-only` and `--write` of earlier versions replaced the configured scopes, so they are gone, and an argument makes the hook refuse every call.
Because it is a settings-level hook, the agent files carry no `hooks:` frontmatter and stay plain Markdown. Denials are written to `security-events.jsonl`.

The scopes of every subagent are in `agentScopes` in `hooks/lib/common.mjs`; `tests/agent-scope.test.mjs` checks that every file under `.claude/agents/` has one, except the main-session agent named by `agent` in `.claude/settings.json`, which must have none.

- `readOnly` (the reviewers, the validator, bi-source-analyst, bi-rdl-analyst): Edit and Write, and any shell command that could change files or git state, are denied. Each statement, pipe stage and nested `$( )`/`{ }` is judged by the program it really runs (folder and `.exe` dropped, git options before the subcommand skipped, `VAR=x`, `env` and `xargs` looked through): redirects, `sed -i` in any position, `sort` with an output option in every spelling `getopt_long` accepts (`--output=f`, `--outp=f`, `--o=f`, `-uof`; audit 2026-11-16) and `uniq IN OUT`, `rm`, `cp`, `tar`, `patch`, `dd`, `find -delete`, every git subcommand that is not a read (`commit`, `config`, `worktree`), `npm install`, interpreters, shells and script files (`node -e`, `py -c`, `powershell -c`, `cmd /c`) and the PowerShell cmdlets and aliases that write (`ni`, `copy`, `Set-Content`, `Expand-Archive`) are denied; the scope reads the shell policy's own writer lists (`subcommandWritesFile`), so `iconv -o`, `sponge`, `yq -i`, `certutil -decode` and a .NET file call are denied to it like `cp` and `tee` (audit 2026-11-17). The validator (also as the npm checks `npm --prefix hardening test` and `run validate`, which take words only after `--`), the RDL comparison (`node hardening/scripts/rdl-compare.mjs`), the hook-pack check (`node hardening/scripts/check-hooks.mjs`, no argument) and harmless version probes (`node --version`) are allowed, each as the whole command: no redirect, no second command, no extra line.
- `write` globs (bi-tmdl-modeler `**/*.SemanticModel/**`, `**/*.tmdl`, `docs/sources/**` and `reports/*/sql/**`; bi-pbir-editor `**/*.Report/definition/**` and `**/*.Report/StaticResources/**` (theme files);
  bi-rdl-editor `**/*.rdl`, `**/*.rds`, `**/*.rsd`, `**/*.rptproj`; bi-ssis-editor `etl/*/**` (a project folder under `etl/`: packages, project files, `sql/` and `jobs/` scripts); bi-doc-generator `docs/**` and `reports/*/docs/**`; the modeler and the RDL editor also get the test folders `docs/tests/**` and `reports/*/tests/**` (the SSIS editor `docs/tests/**` only), the modeler, the PBIR editor, the RDL editor and the SSIS editor `TASKS.md` (bi-doc-generator does not); `tests/agent-scope.test.mjs`): a write outside the scope is denied, and so is any shell command that could change files or git state (the same judgement as `readOnly`): the editors change files only through Edit/Write.
- `mcpReadOnly`: the model editors may read MCP metadata; connection changes, writes and unknown operations go back to the main agent.

output for the CLI's native hooks (a Stop or SubagentStop block stays `{decision, reason}`, which `agentStop` reads; a
PostToolUse block becomes `additionalContext`), adds `modifiedResult`

gate, and denies when the arguments name a secret or data file or a command the shell policy denies, an unknown MCP tool's too (audit 2026-11-17); tools without a policy such as `sql`, `task`, `skill` or `ask_user` are not logged and stay silent). PreToolUse under
Copilot gets no `agent_type`, so the scope guard answers nothing there. Tests: `tests/vscode-hooks.test.mjs`,

`tests/round2-vscode-output.test.mjs`.

When hooks disagree the order is `deny` > `defer` > `ask` > `allow`. Claude Code evaluates settings deny and ask rules whatever a hook returns, in every permission mode (`bypassPermissions` included), a hook's `ask` opens the approval prompt also in Claude Code's auto mode, and in plan mode a hook's `allow` counts only for a read-only call (Claude Code docs, Permissions and Permission modes, checked 2026-10-19). The guard therefore checks the settings deny rules itself (`hooks/lib/permissions.mjs`) and answers `allow` only for routine work in approvals mode `auto` ([README.md](README.md), Approvals). GitHub Copilot evaluates no settings rules, so there the guard asks where an ask rule of the project settings matches a call it did not judge routine and denies where a deny rule matches, whatever its own verdict (`matchingRule` in `hooks/lib/guard-pre-tool-use.mjs`, `hooks/lib/permissions.mjs`).

## MCP policy (Path A with the pack)

- Specific read operations on recognised model tools pass automatically; there is no broad `Get*` match. Writes and unknown operations go to the main agent and the approval flow; the server's own read-only mode stays in force. On a named local connection, ordinary writes (measures, columns, tables, DAX functions, calculation groups, calendars, hierarchies, perspectives, cultures, translations, model properties, transactions; create and update) are a plain ask that `auto` approves and logs; Tier 2 writes (deletes, renames and moves, relationships, partitions, and a partition source, M expression, data source, connection string, provider or named expression named in any table or model write, Power Query expressions, parameters and query groups, refresh, refresh policy, storage mode, database writes) and any other operation always ask (`lab` runs them). Remote or unnamed connections are the floor.
- For DAX execution the pack looks for one known result shape and an integer `maxRows` from 1 to 50; an unrecognised shape asks for review. The query is read from the request's `query` field and nothing else: a call without one, or with a second text that contains `EVALUATE` (a description, a note), asks. Comments (`//`, `--`, `/* */`) are ignored only outside string literals, quoted table names and bracketed names; a string, name or block comment that never closes asks. `TOPN`, `SAMPLE` and `TOPNSKIP` are as row-level as their table (`TOPN(5, Customer)` asks; over `SUMMARIZECOLUMNS` it passes). A query built on `INFO.*`/`INFO.VIEW.*` functions that names no table column returns metadata and passes (`INFO.DATASOURCES` asks). Personal columns: English, Turkish and common European words built in (the SQL read switch's vocabulary, one list for both guards), plus `sources.sqlRead.personalColumns`, which also counts as a whole word of a longer column name when the column is named with its table (`Customer[Home Fax]`). In a table named like a customer, employee, salesperson, contact, person, client, member, patient, student, user or rep, the columns that hold a person's name (`Name`, `Full Name`, `First Name`, `Last Name`, `Display Name`, `<table word> Name` and longer names ending in one of them: `Customer[Name]`, `Employee[Display Name]`, `Customer[Customer First Name]`) ask like the table's key does, anywhere in the query; a manager's or supervisor's name (`Employee[Manager Name]`, `Store[Manager Name]`) asks in any table; `Customer[Country Name]`, `Customer[Company Name]`, `Customer[Account Name]`, `Employee[Department Name]` and `Product[Name]` pass. This is not a DAX parser and not proof that no personal data is present.
- Every alias in `mcp.powerbiServers` (default `powerbi-modeling` and `powerbi-authoring-local`, Microsoft's sample name) and `mcp.powerbiServer` gets the same policy and masking, and so does any server whose tool is one of the modeling server's 21 `*_operations` tools, unless `sources.sqlRead.mcpServers` names it. One agent owns the connection and the writes for a model ([docs/harness/MCP.md](../docs/harness/MCP.md)).
- An MCP tool the policy does not know (no Power BI modeling, GitHub, Figma or SQL-policy call), under Claude Code (audit 2026-11-16, finding 15; audit 2026-11-17): its arguments are read at any depth, nested objects and objects in arrays included. An input that holds a command (`command`, `cmd`, `script`, `commandLine`, or a list of words, with `args`) is judged by the shell policy, an array both joined and quoted, from the `cwd` it names; its deny stands and any other verdict is a floor ask that names the tool. A local file the input names (`file_path`, `filePath`, `file`, `filename`, `path`, `paths`, `source`, `destination` and their siblings, a `file:` uri, taken from the `cwd` when relative) is judged like Read: a secret or data file is denied; `.claude/logs/` and the guard configuration are denied, and a critical file or a reference folder is a floor ask, unless the tool's name says it only reads (a word of the name: `read_file`, `list-directory`), except that a write-side key (`destination`, `output`) is judged as a write whatever the name says; a stream, device or share spelling is judged by its plain spelling and is a floor ask when that tells nothing; any other file keeps no verdict. Past the bounds (depth 10, 5000 values, 1000 files, 25 commands) the call is the floor ask. The Claude desktop app's terminal tool (`mcp__terminal__run_in_terminal`) therefore asks on every call. Under GitHub Copilot (CLI, VS Code, the Claude dialect) an unknown MCP tool or an unmapped tool whose arguments name a secret or data file, or a command the shell policy denies, is denied; the overflow ask, the denies of guard configuration and hook logs and the asks of critical files are not applied there; every other case keeps its earlier handling. Not read: a path with a space under `target`, `from`, `to`, `input` or `output`, a value with a scheme under the new keys, keys of another case, and arguments packed into a JSON string.
- A Power BI connection counts as local (auto-approved ordinary edits) only when its name looks local and the session state records no server for it that is another machine (finding 16). The recorder keeps the remote host a connect request or answer names (the host only, never the connection string) and a later list or get does not erase it; reconnecting under the same name to localhost replaces it. A connect is local only when every server the request names is this machine: `dataSource` and every server key of the connection string (Data Source, Server, Address, Addr, Network Address, Location, Host); a connection string the guard cannot split (a quote, a brace) is not local. The modeling server's own behaviour (the connection name it accepts, the duplicate key it honours, how its answers spell the server) was not checked live: an answer that spells this machine as a fully qualified name makes writes ask ([path-a-live-check.md](../docs/harness/path-a-live-check.md)).
- Where MCP is prohibited (Path B) none of this applies: there is no MCP call to police.

## Security model

| Risk | Control | Limit |
|---|---|---|
| Reading secrets or the data cache | permission rules; PreToolUse file and shell checks; for an MCP tool the policy does not know, the files and commands in its input (Claude Code) | shell analysis is textual; an unknown MCP tool's arguments are not read when packed into a JSON string, and under GitHub Copilot only the denies apply (MCP policy above) |
| Writing a secret into a file | Edit/Write content check, validator, pre-commit, CI | known patterns only |
| Data coming back from MCP | bounded query shape plus `maxRows`; output PII masking | an aggregate can still contain personal data; an answer over Claude Code's MCP output limit is saved to a file the hook never masks: only reads that name the file get the masking (not a wildcard, a copy or a renamed file), and a slice whose keys were stripped (`jq -r '.rows[].Phone'`) gets the text rules only |
| Writing to the wrong model | writes, connection changes and unknown operations ask; deploy denied; a query or write on a connection the session never confirmed asks | the hook knows connection names and the servers the session recorded for them, not whether the model matches the request; a local-looking name is no proof of a local server unless the state records none other (audit 2026-11-16) |
| A query that writes to a database or returns personal rows | SQL read switch: writes denied (also in a text too long to read in full); off by default (every query asks); on: only bounded read-only queries against listed servers without personal columns pass | textual analysis; a query's cost is not bounded |
| A subagent leaving its scope | scoped Edit/Write, read-only MCP, shell write checks | not an OS sandbox |
| The pack's hooks switched off in the settings (a matcher that matches nothing, another event, a timeout that always expires, another type, a word or an argument in the command) | the PreToolUse guard compares each hook entry of the pack with what the settings file holds now, and in the Copilot hook files `.github/hooks/*.json`, and denies a change or removal; adding hooks passes; a change of `env.NODE_OPTIONS`, `env.PATH` or `env.PATHEXT` in the settings and the deletion of a hook file of the pack are denied | managed settings and hook registrations outside `.claude/settings*.json` and `.github/hooks/` |
| A broken commit | validates the staged snapshot of the Git index | not a DAX/TMDL compiler or full JSON Schema validation |
| Per-user files committed (`.pbi/localSettings.json`, `*.tmuo`) | refused when staged, reported when tracked | known file names only |
| A project path spelled differently (symlink, junction, macOS `/tmp`, Windows 8.3 short name, trailing dot, alternate data stream) | the PreToolUse guards check every spelling (as written and resolved); stream and device paths are denied; shell write targets are judged without trailing dots and `:stream`; shell commands are judged with short names spelled out; the file words of every shell program but `echo`, `printf`, `Write-Output` and `Write-Host`, every redirect target and the path of a git `<rev>:<path>` word (`HEAD:b/credentials`) are also judged as the shell opens them, through a link or a `..` after one, a glob by its folder, a PowerShell list by item and a Windows device, local share or stream spelling by its drive path (audit 2026-10-31, A1 and R3 to R5) | a path that is really outside keeps the normal permission flow; a variable, `~`, a wildcard in the first segment and a path a command computes are judged as written |
| A share path (`\\host\share`, `//host/share`) while the project is not on a share | judged as outside without resolving it: the guard opens no connection to a host a command names | a project that is itself on a share still resolves its own paths |
| Force push, bypassing protection | permission, shell and Git hook checks | local hooks can be skipped; require branch protection on the server |

`PostToolUse.updatedToolOutput` changes what the model sees after the tool has run: masking does not undo a network call, a written file or the original telemetry, and a failing hook gives no
guarantee. The first defence is not to request data you do not need. Claude Code's `sandbox.enabled` adds OS-level isolation these hooks do not; enforce organizational policy with Claude Code's
[managed settings](https://code.claude.com/docs/en/settings) (an administrator's file the user cannot override), platform permissions and a required CI check, not repository settings a user can edit.
A single file copied out of a reference folder (`cp templates/t.md docs/x.txt`, `Copy-Item`) is denied and copying the
folder is not (audit 2026-11-16): use Read and Write for one file.
If a credential is found: report file, line and type without the value, then revoke or rotate it; deleting it does not clean Git history, and rewriting history is a human decision.

## Adding a hook

1. Logic in `hooks/lib/` (`policy.mjs` decisions, `validators.mjs` checks); keep the entry script thin.
2. A guard uses `runHook(..., { failClosed: true })`; a logging or context hook is fail-open.
3. A test in `tests/` that triggers it; build a fake secret at run time by joining parts (`tests/copilot-claude-dialect.test.mjs`
   shows the pattern), never as a literal.
4. Register it in `settings.hooks.json` as `node hardening/hooks/<name>.mjs` (no `args`, variables, quotes or inline
   code: Registration above); verify with `npm --prefix hardening test` and `claude --debug`.
